Bilingual input model

Beta B1 does not contain two computational languages. It offers two linguistic input forms that are interpreted before the shared parser.

UTF-8 bytes
   ↓
explicit source profile: es | en
   ↓
spelling classification
   ↓
internal terminal identity
   ↓
single parser
   ↓
single IR 0.3
   ↓
single well-formedness and semantics
   ↓
native Rust / WebAssembly

The selected experimental index classifies each spelling through one joint table and retains, for each entry, its internal identity and the profiles in which it is accepted. Compilation does not traverse a language list sequentially.

B1 properties

  • Profile selection is explicit; there is no language autodetection.
  • The only available selectors are en and es.
  • Changing interface language does not change the source-code profile.
  • Changing the source-code profile does not translate or modify the source.
  • User-defined identifiers, strings, comments and data are not translated.
  • ES/EN differences are resolved before reaching the parser, IR or semantics.
  • Equivalent ES/EN sources retain different provenance and different source_sha256 values.
  • A form belonging to the opposite profile cannot act as valid syntax under the active profile.
  • The web interface transports bytes and invokes local WebAssembly; it does not implement a second semantics.
  • No machine translation, AI, database or remote service is used to determine program meaning.

The seven protected forms without current positive production are PendingU, True, max, min, null, None and NaN. Their protection is part of the version definition; artificially valid programs are not created merely to make those forms productive.

Performance and material cost

In the final joint-index test, adding ES produced no measured increase in allocations, allocated bytes, incremental peak or final live memory when compiling the same English corpus. The added cost is concentrated mainly in code and static tables.

What Beta B1 does not establish

  • It does not yet establish a stable version of SVP-ES.
  • It does not retroactively modify reference Grammar 0.2 or its current reserved-word repertoire.
  • It does not establish a general infrastructure for projects, modules or multiple-file units.
  • It does not enable arbitrary mixing of ES/EN syntax inside one source unit.
  • It does not define Portuguese, French, Italian, German or any other language profile.
  • It does not demonstrate constant cost for an arbitrary number of profiles; each extension must be measured.
  • It does not yet resolve pending work concerning visual Unicode security, structured diagnostics or development tools.

Traceability of future inclusion

A deployed Beta does not become a stable release merely by being publicly accessible. Any future inclusion must identify the exact Beta, its reference version, regression and security evidence, comparison with main, synchronized documentation and the commit ultimately integrated into the main Language repository.

The Beta history preserves B1 state and open proposals for the next revision.
