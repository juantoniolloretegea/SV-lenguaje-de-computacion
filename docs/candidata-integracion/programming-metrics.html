1. Language-profile processing

The experimental architecture resolves the input-language form before parsing. The parser, IR and semantics remain single and do not depend on the selected language.

UTF-8 source
  ├─ es profile → Spanish spelling ─┐
  └─ en profile → English spelling ─┤
                                    ↓
                          joint spelling index
                                    ↓
                         shared internal identity
                                    ↓
                              single parser
                                    ↓
                           AST / IR / semantics

Each joint-index entry relates a spelling to the terminal's internal identity and to the profiles in which it is accepted. A spelling shared between ES and EN is valid only if it represents the same identity in both profiles.

3. Identity and provenance

Computational equivalence does not identify source bytes. The Beta retains the fingerprint of each concrete source and can verify that ES/EN formulations produce the same computational payload without losing provenance.

SemanticPayload(IR_ES) = SemanticPayload(IR_EN)
source_sha256(ES)       ≠ source_sha256(EN)

User identifiers, strings, comments, natural numbers and data are not translated.

5. Measurement method

The final measurement ran against SV-lenguaje-de-computacion@f6b704e819e7d08589f00e9e3f9550deab21d0b1, with rustc 1.98.0 and cargo 1.98.0, on Linux x86-64 over a virtualized AMD EPYC 7763. The configuration comparison alternated all execution orders for 42 rounds; the language-form comparison used 36 rounds.

Three configurations were compared: a single EN profile, sequential bilingual processing, and bilingual processing with a joint index. The length control created an artificial English corpus with the same number of bytes file by file as the Spanish performance corpus.

The −2.671% is not interpreted as acceleration caused by bilingualism.

9. Observed cost of the Spanish form

In the performance corpus, the original English occupied 11865 bytes and Spanish 13371 bytes (+12.693%). The English control was padded with lexically neutral whitespace until matching the Spanish length exactly file by file.

Input languageMedian CPUMAD

ES versus original EN: +2.744%. ES versus the equal-length English control: +2.110%, with 33/36 positive rounds. The test does not permit assigning the differential to one cause: it does not simultaneously equalize word length, terminal distribution, multibyte UTF-8 characters, code points and lexical-comparison structure.

Between ES and the equal-length English control, 0 additional allocations, 0 peak difference, 0 residual memory and only +2.67 requested bytes per compilation were measured.

10. Scalability and limits

  • The architecture avoids an explicit traversal of N profiles through a joint index, but it does not claim mathematically constant physical cost for an arbitrary number of languages.
  • Each future profile must be complete, injective, versioned and compatible with the nominal space defined for its family.
  • A spelling shared by several profiles cannot represent different internal identities.
  • Version compatibility across units and modules must be defined before claiming composition across multiple files.
  • If WebAssembly size becomes material as the number of profiles grows, a distribution or loading strategy must be evaluated without transferring semantic decisions to remote resources.

11. State

Beta B1 remains experimental. The tests demonstrate viability of the ES/EN architecture within the stated scope. Inclusion in the stable version requires a later process and is not determined by this document.
